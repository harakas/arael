# C++ (and Python) interface for arael root models (P11 + generator)

Working plan, 2026-07-25. Two deliverables that validate each other:
the JSON model sidecar (P11) and, as its first consumer, a generator
that produces a C++ interface for a root model. A PYTHON interface
follows from the same machinery: the generated `extern "C"` shim is
exactly what `ctypes` loads, so Python is a third generator backend
over the same C ABI, not a second project. C++ goes first (harder,
shakes out the ABI); Python rides on the result.

## 1. Goal and philosophy

A C++ program builds an arael problem (pushes entities, sets fields,
wires refs), solves it, and reads results -- with the same vocabulary
the Rust side has: `vect3f`, `quaternf`, euler conventions, `Param`
semantics.

API philosophy (agreed): relaxed, not defensive. The C++ developer is
trusted:

- Raw pointers to entities, no handle indirection per field access.
- Unchecked indexing (debug-only asserts).
- No thread-safety promises (one model, one thread; same as Rust `&mut`).
- No lifetime tracking: an entity pointer dies with its model (or its
  Arena slot's removal); that is documented, not policed.
- Everything passed by value where it is POD (math types, configs).

One fact makes this MORE sound than it looks: `refs::Vec` / `Deque` /
`Arena` are chunk-allocated (boxed blocks, elements never move on
push). Raw `Pose*` returned from a push stays valid for the model's
lifetime. The relaxed API is aligned with the storage design, not
fighting it.

## 2. Architecture -- one generator, one C ABI, THREE outputs

The point that extends the original sketch: a C++ header alone cannot
talk to the model. Model structs are `repr(Rust)` -- field offsets are
unknowable outside rustc, and collections have private internals. So
the generator must emit the bridge itself:

1. **Rust FFI shim** (`<root>_ffi.rs`): `#[no_mangle] extern "C"`
   functions compiled in a small user-owned `cdylib`+`staticlib` crate
   that depends on the model crate. Rustc knows the offsets; the shim
   is where all `unsafe` lives. Its surface is PURE C ABI (pointers,
   `uint32_t`, `#[repr(C)]` PODs) -- deliberately, because it serves
   two consumers:
2. **C++ header** (`<root>.hpp`): thin inline wrapper classes over
   those symbols, using the arael math headers for value types.
3. **Python module** (`<root>.py`, later stage): `ctypes` classes over
   the SAME symbols loaded from the cdylib. No compiled Python
   extension, no new ABI -- a second skin on the substrate the C++
   work already hardened.

All generated by ONE tool from ONE JSON sidecar: **`cargo-arael`**, a
Rust cargo subcommand (the `cargo-<sub>` binary naming is cargo's
discovery convention, so the crate name is fixed). Internally it
parses JSON into a small model IR once and runs per-target emitters
(`emit_ffi_rs`, `emit_hpp`, `emit_py`, `emit_cmake`) over it, so
backends cannot drift from each other or from the model. The
C-ABI-purity rule is what keeps Python nearly free: any signature a
C++ convenience would like (overloads, references, templates) stays in
the header skin, never in the shim.

Alternatives considered and rejected:
- **cxx / cbindgen crates**: exactly the conservative APIs we do not
  want (handle types, checked everything, no math vocabulary), and
  they cannot see arael's layout semantics (params, refs, containers).
- **Macro-emitted shim** (`#[arael(root, cxx)]`): keeps codegen in
  Rust, but the C++ header still needs a separate generator, splitting
  one interface across two generators in two languages.
- **Python generator script**: the original sketch. Dropped on the
  distribution question -- there is no good answer to "where does the
  user get the Python tool" for a Rust/C++ audience, while the model
  author by definition has cargo. A cargo subcommand also gets to
  DRIVE the pipeline (build with the sidecar enabled, harvest the
  JSON, emit everything) instead of being a manual middle step.
  Cost accepted: generator iteration is slower in Rust and codegen
  is wordier.

## 3. The JSON sidecar (P11 proper)

### Emission

Env-gated at root expansion (no source changes needed on any existing
model): `ARAEL_SIDECAR_DIR=<dir> cargo build` writes `<dir>/<Root>.json`
for every root that expands. The macro has everything at that point:
the reachable set, layouts, containment paths, refs, constraints.

### Macro extension required

`SymFieldType` collapses data fields (`f64`, `bool`, `u32`, `String`,
user types all become `Scalar` or `Struct(name)`), and the C++
generator needs real spellings to type getters. Add to `SymLayout` a
parallel record `spelled_types: Vec<(String, String)>` -- field name
to type spelling as written -- captured at classification. Small,
additive, invisible elsewhere.

### Schema v1 (draft -- stable once shipped, carries `"schema": 1`)

```json
{
  "schema": 1,
  "root": "World",
  "precision": "f32",
  "types": {
    "World": {
      "role": "root",
      "param_count": 0,
      "fields": [
        {"name": "poses", "kind": "collection", "container": "vec", "of": "Pose"},
        {"name": "ties",  "kind": "collection", "container": "std_vec", "of": "Tie"}
      ]
    },
    "Pose": {
      "role": "entity",
      "param_count": 6,
      "self_block": "hb",
      "fields": [
        {"name": "ea",    "kind": "euler_param", "variant": "simple", "scalar": "f32", "params": 3},
        {"name": "pos",   "kind": "param", "of": "vect3f", "params": 3},
        {"name": "stamp", "kind": "data",  "of": "f64"},
        {"name": "note",  "kind": "opaque", "of": "String"},
        {"name": "gps",   "kind": "optional", "of": "GpsObs"},
        {"name": "hb",    "kind": "self_block", "scalar": "f32"}
      ]
    },
    "Tie": {
      "role": "entity",
      "param_count": 0,
      "fields": [
        {"name": "a",  "kind": "ref", "of": "Pose", "target": "root.poses"},
        {"name": "b",  "kind": "ref", "of": "Pose", "target": "root.poses"},
        {"name": "dt", "kind": "data", "of": "vect3f"},
        {"name": "dr", "kind": "data", "of": "matrix3f"},
        {"name": "hb", "kind": "cross_block", "a": "Pose", "b": "Pose", "scalar": "f32"}
      ]
    }
  },
  "constraints": [
    {"on": "Tie", "label": "tie", "file": "src/model.rs", "line": 41}
  ]
}
```

Field `kind` values: `data` (scalar or math type, spelled in `of`),
`param` (`of` = inner type), `euler_param` (variant simple / universal
/ rotvec), `component` (`of` = component type, expanded like a nested
struct), `struct` (nested sub-model), `optional`, `collection`, `ref`,
`self_block` / `cross_block` / `triplet_block` (generator skips
blocks), `skip`, `opaque` (present but no accessor; generator lists
them in a header comment so nothing silently disappears from view).

Constraints are informational (labels for diagnostics), not needed for
the interface.

### Sidecar tests

A fixture root built with `ARAEL_SIDECAR_DIR` set in a `std::process`
driven test; assert the parsed JSON against expected structure. Schema
documented in `docs/SIDECAR.md`.

## 4. The C++ math library (hand-written, not generated)

Header-only, C++17, no dependencies. Lives in the `cargo-arael` crate
(`cargo-arael/headers/arael/`) so it ships with the tool and gets
vendored, version-stamped, into every generated tree:

| Header | Types | Mirrors |
|---|---|---|
| `vect.hpp` | `vect2<T>`, `vect3<T>` + `vect2f/2d/3f/3d` | `{x, y}` / `{x, y, z}` |
| `matrix.hpp` | `matrix2<T>`, `matrix3<T>` + f/d aliases | `{ rows[N] }`, row-major, rows are vectors |
| `quatern.hpp` | `quatern<T>` + f/d aliases | `{t, v}` -- scalar FIRST, then vect3 |
| `math.hpp` | umbrella + free functions | |

Operator conventions copied from Rust arael exactly, including the
unusual one: `*` between vectors is DOT product, `%` is CROSS product,
`matrix * vect` / `matrix * matrix` / `quat * quat` / `quat * vect`
compose as in Rust. Named `dot()` / `cross()` also provided for C++
readers who blink at `%`.

Operations to port (inventory pass over vect.rs / matrix.rs /
quatern.rs / geometry helpers at implementation time): norms,
normalize, index by int, rotation constructors
(`matrix3<T>::rotation_x/y/z`, `from_euler` with the project
convention **x=roll, y=pitch, z=yaw, R = R(z)*R(y)*R(x)**), quatern
from/to rotation matrix, from/to euler, slerp if present, exp-map
small-rotation helpers used by the params.

Layout compatibility: the Rust types are `repr(Rust)` but plain
single-scalar structs; the FFI does NOT gamble on that. The shim
declares `#[repr(C)]` mirror structs (`CVect3<T> {x, y, z}` etc.) with
`From` conversions both ways (field-by-field; the optimizer flattens
them to nothing). C++ headers `static_assert` size/alignment of their
own types against the C mirrors' documented layout.

Parity tests: a Rust `#[test]` writes golden values (rotations,
quaternion round trips, euler conversions at awkward angles) to a
generated header of constants; a C++ test program (built by a `cc`
build script in the test crate) computes the same and compares to
1 ulp-ish tolerances. The euler convention CANNOT drift silently.

## 5. FFI conventions

- **Opaque root handle**: `World* world_new()`, `world_free(World*)`.
  C++ class `arael::World` owns it, RAII (the one non-relaxed thing --
  a destructor costs nothing and prevents the dumbest leak). Move-only.
- **Entity access**: `Pose* world_poses_push(World*)`,
  `Pose* world_poses_at(World*, uint32_t)`, `uint32_t world_poses_len(World*)`.
  Returned pointers are stable (chunked storage); wrapper class
  `PoseRefMut { Pose* p; }` with inline field methods. Per-field calls
  take the entity pointer directly -- no repeated container walk.
- **Field accessors**: `pose_pos(const Pose*) -> CVect3f`,
  `pose_set_pos(Pose*, CVect3f)`; params read/write `.value`. Data
  fields likewise. Opaque fields: skipped, listed in a comment.
- **Euler/quaternion/transform params**: semantic accessors generated
  per variant -- `pose_set_ea_euler(Pose*, CVect3f)`,
  `pose_set_ea_quat(...)` where the representation supports it,
  matching whatever the Rust-side setting idiom is (checked at
  implementation: reference-frame components need their reset path,
  not raw field pokes).
- **Refs**: `Ref<T>` is one `u32` (index+generation packed) -- crosses
  the FFI as `uint32_t`. C++ wraps it in `Ref_Pose { uint32_t raw; }`
  typed per target so `tie.set_a(...)` cannot take a landmark ref by
  accident. Obtained from `push()` returns and `ref_at(i)`.
- **Option entities**: `pose_has_gps`, `pose_make_gps` (inserts
  default-ish/zeroed, returns `GpsObs*`), `pose_clear_gps`,
  `pose_gps` (nullable pointer). The Some/None flip between solves
  rule is documented, not enforced.
- **Nested sub-models**: same pattern one level down
  (`path_poses_push(Path*)` -- accessors hang off the OWNING struct's
  pointer, so nesting costs nothing).
- **Solve**: `world_solve_dense(World*, const CLmConfig*, CLmResult*) -> int32 status`,
  same for `solve_sparse`. `CLmConfig` mirrors the useful `LmConfig`
  subset (`max_iters`, `min_iters`, `patience`, `abs_precision`,
  `rel_precision`, `initial_lambda`, target-cost early-out) plus a
  `preset` enum (default / conservative). `CLmResult` carries
  `start_cost`, `end_cost`, `iterations`, `accepted_iterations`,
  `status`, exit `lambda`. Params live in the model afterwards -- read
  them back through field getters; no param-vector surface in v1.
- **Panics**: solve/validate entry points wrap in `catch_unwind`;
  a panic (e.g. the unguarded-Option read) returns a distinct status
  and the message via `world_last_error(World*) -> const char*`
  (buffer owned by the handle, valid until the next call). Setters and
  getters are raw -- they cannot panic in practice and stay zero-cost.
- **validate()**: `world_validate(World*) -> const char*` -- empty
  string when clean, the Diagnostic's Display text otherwise. Cheap,
  invaluable for C++-side model-building mistakes.
- **Precision**: generated per root at its concrete precision (an f32
  root yields float costs/configs). No templates in generated code.

## 6. Worked example

Rust model (the SLAM-ish shape):

```rust
#[arael::model]
struct Pose {
    ea: SimpleEulerAngleParam<f32>,
    pos: Param<vect3f>,
    stamp: f64,
    hb: SelfBlock<Pose, f32>,
}

#[arael::model]
#[arael(constraint(hb, { /* ... */ }))]
struct Tie {
    #[arael(ref = root.poses)] a: Ref<Pose>,
    #[arael(ref = root.poses)] b: Ref<Pose>,
    dt: vect3f,
    dr: matrix3f,
    hb: CrossBlock<Pose, Pose, f32>,
}

#[arael::model]
#[arael(root, f32)]
struct World {
    poses: refs::Vec<Pose>,
    ties: std::vec::Vec<Tie>,
}
```

Generated C++ usage:

```cpp
#include <arael/math.hpp>
#include "world.hpp"        // generated

using namespace arael;

World w;
auto p0 = w.poses().push();
p0.set_pos({0, 0, 0});
p0.set_ea_euler({0.0f, 0.1f, 0.2f});   // roll, pitch, yaw
p0.set_stamp(12.5);
auto p1 = w.poses().push();
// ...

auto t = w.ties().push();
t.set_a(p0.ref());
t.set_b(p1.ref());
t.set_dt({1, 0, 0});
t.set_dr(matrix3f::rotation_z(0.1f));

LmConfig cfg = LmConfig::defaults();
cfg.max_iters = 50;
LmResult r = w.solve_sparse(cfg);
if (r.status != LmStatus::Converged)
    fprintf(stderr, "solve: %s\n", w.last_error());

vect3f pos = p0.pos();                 // optimized value, same pointer
for (uint32_t i = 0; i < w.poses().size(); i++)
    use(w.poses()[i].pos());
```

Generated header shape (excerpt):

```cpp
namespace arael {

struct Ref_Pose { uint32_t raw; };

class PoseRef {           // const view; PoseRefMut adds setters
public:
    vect3f  pos() const      { return ffi::pose_pos(p_); }
    vect3f  ea_euler() const { return ffi::pose_ea_euler(p_); }
    double  stamp() const    { return ffi::pose_stamp(p_); }
    // field `note`: String -- opaque, no accessor generated
private:
    const ffi::Pose* p_;
};

class World {
public:
    World() : h_(ffi::world_new()) {}
    ~World() { if (h_) ffi::world_free(h_); }
    World(World&&) noexcept;             // move-only
    PosesView poses();                   // push/at/size/ref_at/iter
    TiesView  ties();
    LmResult  solve_dense(const LmConfig&);
    LmResult  solve_sparse(const LmConfig&);
    const char* validate();              // "" when clean
    const char* last_error() const;
private:
    ffi::World* h_;
};

} // namespace arael
```

Generated Rust shim shape (excerpt):

```rust
#[no_mangle]
pub unsafe extern "C" fn pose_set_pos(p: *mut Pose, v: CVect3f) {
    (*p).pos.value = v.into();
}

#[no_mangle]
pub unsafe extern "C" fn world_poses_push(w: *mut World) -> *mut Pose {
    let r = (*w).poses.push(Pose::default());
    &mut (*w).poses[r] as *mut Pose
}

#[no_mangle]
pub unsafe extern "C" fn world_solve_sparse(
    w: *mut World, cfg: *const CLmConfig, out: *mut CLmResult) -> i32 {
    match std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        (*w).solve_sparse(&(*cfg).to_lm_config())
    })) { /* fill out, stash error string, return status */ }
}
```

Requirements this puts on the model crate (documented): structs and
fields `pub` (same rule as `export_models!`), entities constructible
empty (`Default` or a generated zero-init -- decided at
implementation; blocks/params all have obvious zero states).

## 7. Field-kind to API mapping (the generator's core table)

| JSON kind | C++ surface |
|---|---|
| `data` scalar (`f32/f64/bool/u32/i32/usize`) | `T x() const` / `set_x(T)` |
| `data` math (`vect2/3`, `matrix2/3`, `quatern`, f/d) | by-value get/set with arael-cxx types |
| `param` of scalar | `T x() const` / `set_x(T)` (reads/writes `.value`) |
| `param` of vect2/3 | by-value get/set |
| `euler_param` simple | `set_x_euler(vect3)` / `x_euler()` (+ quat forms where the Rust API allows) |
| `euler_param` universal / rotvec, `component` (Transform/UnitVec) | semantic set/get via the component's own reset path |
| `ref` | `Ref_T x() const` / `set_x(Ref_T)` |
| `optional` entity | `has_x` / `x()` nullable / `make_x()` / `clear_x()` |
| `struct` (nested) | `x()` returns child view class |
| `collection` | view with `push` / `size` / `operator[]` / `ref_at` / iteration; Arena adds `remove(Ref_T)` |
| `self/cross/triplet_block`, `skip` | nothing |
| `opaque` | nothing + header comment listing it |

## 7b. The Python skin (planned now, built after C++)

`ctypes` over the cdylib -- no compiled extension module, works on any
CPython, nothing to build on the consumer side beyond the cdylib the
C++ path already produces.

- **Generated module** `world.py`: `World`, entity view classes, and
  typed ref wrappers mirroring the C++ classes one-to-one. Fields
  become properties: `p.pos = (0.0, 0.1, 0.2)`; `p.pos` returns a
  small `vect3` namedtuple-ish class (stdlib only in the core).
  Math values accept any length-matching sequence on the way in.
- **numpy**: optional convenience layer, not a dependency -- accepted
  transparently where a sequence is (numpy scalars/arrays satisfy the
  sequence protocol); a helper to bulk-read a collection's params into
  an array can come later if profiling asks for it.
- **Errors**: nonzero solve status raises `AraelError(status, message)`
  built from `world_last_error` -- panics become exceptions, which is
  the Pythonic contract for free.
- **GIL**: `ctypes` releases the GIL around foreign calls, so long
  solves do not block other Python threads -- no extra work needed.
- **Testing**: the same parity idea as cxx-tests -- build the fixture
  problem in Python, solve, compare against the Rust solve; plus
  golden-file tests for the emitted module. Python's dynamism makes
  this the cheapest end-to-end harness of the three, another reason
  the backend is nearly free once the shim exists.
- **Use case to keep in view**: the python benchmark harnesses (GTSAM
  comparisons run through python bindings today) -- an arael python
  skin lets arael slot into the same scripts.

## 8. The tool: `cargo-arael`

A new workspace crate publishing the `cargo-arael` binary
(`cargo install cargo-arael`; invoked as `cargo arael <sub>`).
Subcommands:

- **`cargo arael export`** -- the whole pipeline in one step, run in
  the model crate's directory:
  1. `cargo build` the model crate with `ARAEL_SIDECAR_DIR` pointed at
     `target/arael-sidecar` (the env var becomes an internal
     mechanism; still documented for manual use).
  2. Parse the harvested `<Root>.json` (one interface per root;
     several roots share one capi crate).
  3. Emit the generated tree (layout in section 8b): capi shim crate,
     C++ header, vendored math headers, CMakeLists, Python module.
- **`cargo arael check`** -- regenerate to a temp dir, diff against
  the committed tree, nonzero exit on drift. The CI staleness guard
  for committed artifacts.
- **`cargo arael package`** (late stage) -- build release artifacts
  and produce a prebuilt distribution tarball: `include/`,
  `lib/libmymodel_capi.{a,so}`, `mymodel.py`, and a CMake config-file
  package (`mymodelConfig.cmake`) so downstream does
  `find_package(mymodel)` with NO Rust toolchain at all.

Implementation: plain Rust, serde_json for the sidecar, codegen via
string building (no template engine). The math headers ship inside
the cargo-arael crate and are copied (vendored, version-stamped) into
the generated tree, so a generated interface is self-contained.

Testing: golden-file tests in the cargo-arael crate (fixed JSON in,
byte-exact expected outputs); end-to-end integration mirrors
`export-tests/` -- a `cxx-tests/` mini-workspace with (a) a small
model crate, (b) the generated capi crate, (c) a C++ `main.cpp` built
via the `cc` crate in a test build script, asserting: build a problem
in C++, solve, compare cost/params against the SAME problem built and
solved in Rust (numeric parity is exact for identical inputs -- the
solver is deterministic). CI guards: skip C++ tests when no C++17
compiler is present; the CMake-glue test additionally requires cmake.

## 8b. Consumer build and distribution -- the path

Model author (writes Rust, owns the interface):

```
cargo new mymodel --lib        # pub #[arael::model] structs + root
cargo install cargo-arael      # once
cargo arael export             # generate everything
git add capi cxx py && git commit
```

Generated tree, committed alongside the model:

```
mymodel/
  src/lib.rs             # hand-written model -- the ONLY authored file
  capi/                  # generated shim crate
    Cargo.toml           #   crate-type = ["cdylib", "staticlib"],
    src/lib.rs           #   depends on mymodel + arael
  cxx/
    include/arael/*.hpp  # vendored math headers (version-stamped)
    include/mymodel.hpp  # generated interface
    CMakeLists.txt       # generated build glue
  py/
    mymodel.py           # generated ctypes module
```

C++ consumer (needs a C++17 compiler + a Rust toolchain in
source-build mode):

```cmake
add_subdirectory(path/to/mymodel/cxx)     # or FetchContent
target_link_libraries(app PRIVATE arael::mymodel)
```

The generated CMakeLists is self-contained (~30 lines): an
`add_custom_command` that runs `cargo build --release -p mymodel-capi`
plus an IMPORTED target carrying include dirs, the built library, and
platform link libs (Linux/mac in v1). No CMake-Rust framework
dependency; corrosion is documented as the alternative for consumers
who already use it.

Python consumer: build the cdylib once (`cargo build --release -p
mymodel-capi`, or let the CMake build do it), then `import mymodel` --
the generated module resolves the cdylib next to itself and in
`target/release`, overridable with `ARAEL_LIB=<path>`.

Prebuilt mode (`cargo arael package`, later): consumers get the
tarball and neither cargo nor rustc -- `find_package(mymodel)` or
`import mymodel` directly. The source-build CMake output and the
config-file package share layout so switching modes is a no-op for
consumer code.

**Stage 0 -- JSON sidecar (P11). [DONE 2026-07-25]**
`spelled_types` in SymLayout (recorded at the top of classification so
skip/deriv fields are included); `arael-macros/src/sidecar.rs` with a
dependency-free JSON writer; env-gated emission at root expansion;
schema v1 documented in `docs/SIDECAR.md`. Unit tests build registries

SymLayout-literal test helper that had been silently broken since the

**Stage 1 -- math headers. [DONE 2026-07-25]**
`cargo-arael/headers/arael/{vect,matrix,quatern,math}.hpp`, C++17

**Stage 2 -- cargo-arael skeleton, scalar-only end-to-end. [DONE 2026-07-25]**
The crate (lib + `cargo-arael` bin, workspace member), `export`
driving the sidecar build (touches sources to defeat the fingerprint,

sentinel-based LmConfig (UINT32_MAX/NaN = keep preset), LmResult,
validate, last_error. `Param<T>` gained `Default` in arael (blocks
already had it) for the push()-returns-zeroed contract.
`cxx-tests/` workspace: fixture model (root params + root.hb
observations in std vec + own-param entities in refs::Vec + opaque
String), committed generated tree, parity test comparing EVERY value

## 10. Decisions (settled 2026-07-25) and open questions

Settled:

1. Generator emits the Rust shim too (repr(Rust) makes a header-only
   approach impossible). AGREED.
2. Sidecar gating: `ARAEL_SIDECAR_DIR` env var, set internally by
   `cargo arael export`; documented for manual use. RESOLVED by the
   tool design.
3. Generated artifacts are COMMITTED in the model repo;
   `cargo arael check` is the CI staleness guard. RESOLVED.
4. `%` is cross product in C++, mirroring Rust arael; named `cross()`
   alongside. AGREED.
5. `push()` returns a zeroed entity to fill -- model structs need
   `Default` (or a generated zero-init). AGREED.
6. Shim crate builds `["cdylib", "staticlib"]` -- Python needs the
   cdylib, C++ links either. RESOLVED.
9. Generator language: Rust, as the `cargo-arael` cargo subcommand
   (crate name fixed by cargo's `cargo-<sub>` discovery convention).
   AGREED -- distribution and pipeline integration outweigh slower
   codegen iteration.

7. v1 scope: covariance export, observer callbacks, band solve, and
   ExtendedModel are OUT (both skins). AGREED. Covariance, observer
   callbacks, and band solve are PLANNED FOR V2 -- the C ABI should
   not paint them into a corner (an iteration-callback slot is a
   function pointer + user data pointer; covariance is a bulk read
   into a caller buffer; band is `solve_band(cfg, kd)` -- all fit the
   existing conventions). ExtendedModel: probably never exposed.
8. Python core stays stdlib-only (numpy accepted where sequences are,
   never required). AGREED.

All questions settled; the plan is ready to execute.
